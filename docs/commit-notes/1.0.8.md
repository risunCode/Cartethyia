## Failover Rewrite (user's prime concern)

### Problem
A 429 with an empty/opaque body was classified as `quota_exceeded`, triggering
a full 5-minute cooldown on the first transient blip. Accounts went offline on
a single hiccup even though they were still usable.

### 3-tier error classification
- **T1 known** (rate-limit, quota, model-capacity) → cooldown with per-reason backoff
- **T2 transient** (5xx, network, stream, protocol, unknown) → NO cooldown, account stays eligible
- **T3 permanent** (invalid request, client abort) → no cooldown, skip entirely

### Graduated backoff
- Opaque/unknown 429s start at 30s base, grow exponentially with `failureCount`
- Full 5-min default only after 3 failures (`RATE_LIMIT_GRADUATED_THRESHOLD`)
- One transient blip no longer disables an account

### Cooldown caps lowered
- Account quota: 24h → 5 min
- Account rate-limit: 30 min → 5 min
- Auth backoff: 30 min → 5 min
- SERVER_ERROR/UNKNOWN: 20s/5min → 0 (transient, no cooldown)

### Account recovery sweep
- `AccountRecoverySweep` (`src/app/recovery-sweep.ts`) — unref'd 1-min interval
- Transitions expired cooldowns → `healthy` via `recordSuccess`
- Clears expired per-model locks (was dead code)
- Zero per-request overhead

### Per-model account locking
- Error on `claude/sonnet-4` no longer blocks `claude/haiku-4` on same account
- New `account_model_locks` table with composite key `(account_id, model_id)`
- `AccountHealthManager.recordModelLock`/`clearModelLock` + routing candidate filter

### Sticky round-robin fix
- Pool created when `eligible.length >= stickyLimit` (was `>`, silently disabled sticky)
- In-flight aware: idle accounts (in-flight=0) preferred over busy within sticky pool
